# 구조와 메시지 흐름

이 엔진은 **하나의 게임을 하나의 서버 프로세스에서 운영**하는 구조다. 한 프로세스에 여러 게임방을 만들 수 있으며, 서로 다른 게임 서버의 플레이어 목록이나 룸은 공유하지 않는다. 기본 실행에는 외부 서비스가 필요 없다. 계정 인증과 영속 저장이 필요하면 게임 애플리케이션이 연결한다.

처음 읽는다면 이 문서로 역할을 확인한 뒤 [게임 확장 인터페이스](interfaces.md), [클라이언트 프로토콜](protocol.md) 순서로 읽으면 된다.

## 액터와 메시지 큐

액터는 자신이 관리하는 상태와 메시지를 처리하는 작업을 묶은 단위다. 다른 코드가 룸의 게임 상태를 직접 바꾸는 대신, 룸에 메시지를 보내면 룸이 순서대로 처리한다. 한 방에서 두 사람이 동시에 행동해도 `GameLogic::on_event`는 한 번에 하나씩 실행된다. 서로 다른 방은 독립적으로 실행된다.

이때 메시지가 도착해서 처리되기까지 머무는 큐를 **mailbox**라고 한다. **bounded**는 큐에 담을 수 있는 개수에 상한이 있다는 뜻이다. 처리보다 입력이 계속 빠를 때 메모리가 끝없이 늘지 않도록 제한한다. 큐가 가득 찬 경우에는 거절하거나 느린 연결을 끊는 정책이 필요하다.

**Handle**은 액터에 메시지를 보내는 서버 내부 객체다. `RoomHandle`을 복제해도 룸이나 게임 상태가 복사되지는 않는다. 같은 룸을 가리키는 전송 경로를 하나 더 얻는다. 브라우저에는 핸들 대신 룸 ID와 패킷 규약만 노출된다.

Tokio는 여러 비동기 작업(task)을 정해진 수의 스레드에서 실행한다. 네트워크를 기다리는 동안 다른 task가 실행될 수 있다. 다만 룸 콜백에서 동기 DB 호출이나 긴 계산을 하면 그 콜백과 같은 실행 자원을 사용하는 작업이 지연된다. 액터 모델을 사용해도 콜백을 짧게 유지해야 한다.

## 플레이어, 세션, 연결의 차이

| 용어 | 의미 |
|---|---|
| `Principal` | 인증된 주체. 계정(`account`) 또는 임의로 발급한 게스트(`guest`)의 식별자 |
| `SessionId` | 이번 게임 접속의 논리 세션 ID. 계정 ID와 별개이며 재접속 유예 안에서는 유지됨 |
| `Player` | 세션 ID, Principal, 닉네임과 프로필 이미지 주소의 스냅샷 |
| WebSocket 연결 | 현재 데이터를 주고받는 실제 네트워크 연결. 끊겼다가 새로 열 수 있음 |
| `generation` | 같은 논리 세션의 연결을 교체할 때 증가하는 세대 번호. 오래된 연결의 입력·종료 처리가 새 연결에 영향을 주지 않도록 사용 |

예를 들어 모바일 네트워크가 바뀌면 WebSocket은 끊어질 수 있지만, 논리 세션과 방 안의 캐릭터까지 즉시 삭제할 필요는 없다. 엔진은 이 둘을 분리해 기본 60초 동안 재접속을 허용한다. 한 계정에는 이 프로세스에서 하나의 논리 세션만 허용한다. 새 게스트 인증은 새 주체를 만들기 때문에 이전 게스트를 이어 하려면 재접속 인증을 사용해야 한다.

## 각 모듈의 책임

| 모듈 | 소유·관리하는 것 | 사용하는 상황 |
|---|---|---|
| 접속 task / 클라이언트 계층 | 실제 소켓, 입력 해석, 승인된 룸 경로, 연결별 출력 큐 | 패킷 수신·송신, Ping/Pong, 연결 종료 |
| `SessionManager` | 논리 세션, 계정 중복 접속, 재접속 토큰·기한, 연결 여부 | 접속·복구·최종 해제, 신뢰된 서버의 수신자 조회 |
| `RoomManager` | 룸 생성·회수, 세션별 참가 색인, 입장·퇴장 조정 | 방 생성·참가·퇴장, 룸 종료 감독 |
| 룸 액터 + `GameLogic` | 해당 룸의 참가자와 게임 상태 | 입장 정책, 게임 입력·주기 이벤트 처리, 상태 전송 |
| `Matchmaker` | FIFO 매칭 대기열 | 정해진 인원이 모이면 게임방 생성·참가 |
| `Engine` | 위 모듈의 시작·종료와 호출 창구 | 서버 시작, 게임별 설정, 관리 API 사용 |

코드에서 클라이언트 계층은 `actors/client.rs`의 `ClientHandle`·`ClientInbox`와 `server.rs`의 접속 task로 나뉜다. `ClientHandle`은 논리 세션 동안 유지되고, 연결이 바뀔 때 실제 출력 큐인 `ClientInbox`가 교체된다.

### 글로벌 룸과 SessionManager는 왜 다른가

글로벌 룸은 **room ID 0인 실제 룸**이다. 이 게임 서버의 모든 인증된 플레이어가 자동 참가하고, 일반 게임방에 들어가도 글로벌 참가를 유지한다. 재접속 유예 중인 플레이어도 남아 있다. 서버 공지나 게임 전체 로비 로직을 `GameLogic`으로 구현할 수 있다.

SessionManager는 접속과 신원을 관리한다. 글로벌 룸도 게임 상태와 콜백을 가진 룸이므로, 전체 인원과 관련되어 있다는 이유만으로 세션 관리까지 맡지는 않는다. 글로벌 룸 참가자 목록도 “지금 연결된 사용자만의 목록”은 아니다.

기본 설정에서는 클라이언트가 글로벌 룸으로 게임 입력을 보내면 `denied`다. 신뢰된 서버 코드의 글로벌 방송은 가능하다. 글로벌 룸은 모든 플레이어에게 영향을 주므로 콜백을 짧게 유지하고, 불필요한 전체 방송을 피한다.

### 방장 생성과 자동 매칭

사용자가 방을 만드는 게임은 `create` 후 상대가 `join`한다. 생성자가 방장으로 기록된다. 매칭형 게임은 `queue`로 기다리고, `match_size`만큼 유효한 후보가 모이면 엔진이 방을 만든다. 두 경로는 같은 RoomManager와 룸 입장 검사를 사용한다. 방장은 생성자 또는 첫 매칭 후보이며, 최종 퇴장 시 자동 승계하지 않는다.

기본값은 글로벌 룸과 게임방 하나까지 참가할 수 있다. 게임에 따라 `allow_create`, `allow_join`, `allow_queue`를 제한하거나 `match_size=0`으로 기본 매칭을 끈다. 기본 매칭은 먼저 대기한 순서인 FIFO다. 실력·지역 등을 고려하는 매칭 정책은 애플리케이션에서 구현한다.

## 실제 입력과 출력의 경로

인증과 방 생성 같은 제어 요청은 게임 입력과 분리되어 있다.

```text
브라우저 ── AUTH ──> 접속 task ──> Authenticator ──> 세션 등록·글로벌 입장
        <─ WELCOME ─┘

브라우저 ── COMMAND ──> 접속 task ──> Engine ──> 룸 생성·참가 / 매칭
        <─ REPLY ─────┘

브라우저 ── GAME ──> 접속 task ──> 승인된 RoomHandle ──> 룸 mailbox
                                                           │
                                              GameLogic::on_event
                                                           │
브라우저 <─ WebSocket <─ 연결별 출력 큐 <─ ClientHandle <─ RoomContext
```

게임 입력은 프레임 크기·전송률, 참가 경로와 연결 세대를 검사한 뒤 해당 룸으로 간다. **매 입력마다 SessionManager나 RoomManager를 왕복하지 않는다.** 게임은 서버가 확인한 `Message.player`로 발신자를 식별하고, 이동 거리·턴·자원 등 게임 규칙을 추가로 검사한다.

출력할 때 게임은 `RoomContext.send` 또는 `broadcast`에 게임별 데이터만 넘긴다. 엔진이 현재 룸 ID와 opcode를 붙여 연결별 출력 큐로 보낸다. 브로드캐스트는 인코딩한 프레임을 공유한다. 느린 수신자의 출력 큐가 가득 차면 해당 연결을 종료하고 다른 수신자 처리를 계속한다.

메시지를 큐에 넣는 데 성공했다는 것은 실제 클라이언트가 받거나 적용했다는 뜻은 아니다. 확실한 완료 확인이 필요한 행동은 게임 규약에 응답·ACK를 정의한다. 클라이언트가 임의 상대를 지정해 게임로직 없이 중계하는 기본 패킷은 없다. 서버 내부의 신뢰된 M:N 전송 API는 [인터페이스 문서](interfaces.md#인증신뢰된-mn-전달)에 설명되어 있다.

## 연결이 끊어졌을 때

1. 접속 task가 소켓 종료나 Ping/Pong 실패를 감지하면 현재 연결을 중지한다.
2. 게임에는 `Disconnected`가 전달된다. 세션과 룸 참가·게임 상태는 유예 동안 유지하고 매칭 대기는 취소한다.
3. 유예 안에 올바른 재접속 인증을 보내면 같은 세션에 새 연결을 붙이고 `Reconnected`를 전달한다.
4. 게임은 이 이벤트에서 현재 상태 스냅샷을 보낸다. 스냅샷은 클라이언트가 현재 화면을 다시 구성할 수 있는 데이터다.
5. 유예가 만료되면 최종 퇴장인 `Left`가 전달되고 참가 상태를 제거한다.

유효한 재접속은 서버가 기존 연결의 끊김을 감지하기 전에도 연결을 교체할 수 있다. Ping/Pong은 끊김 감지용이고, 재접속 유예는 감지 후 상태 보존 기간으로 별도 설정이다. 브라우저는 WebSocket Pong을 자동 처리한다.

오프라인 출력·입력 재전송·프로세스 재시작 복구는 제공하지 않는다. 재접속 시 최신 상태를 보내는 예제와 인증 형식은 각각 [인터페이스](interfaces.md), [프로토콜](protocol.md)에 있다.

## 게임 개발 시 바꾸는 부분

- 게임 규칙과 방 상태: `GameLogic` 구현. 게임방마다 별도 인스턴스가 만들어진다.
- 클라이언트 명령과 상태 표현: 게임별 opcode와 payload 규약.
- 계정 인증: `Authenticator` 구현. 기본 `GuestAuth`는 게스트 접속만 지원한다.
- 저장·외부 API 같은 비동기 작업: 게임이 관리하는 제한된 worker와 `RoomHandle::event`로 결과 반환.
- 추가 제어 API: 필요한 경우에만 `server::Application` 사용. 일반 GAME 입력은 이 훅을 거치지 않는다.

영속 저장, 분산 서버, 재시작 복구는 기본 엔진 밖의 기능이다. 코드 위치는 `src/actors/`가 액터, `src/game.rs`가 게임 인터페이스, `src/server.rs`가 WebSocket 전송 계층이며, 바로 실행할 게임 구현은 [`examples/custom_game.rs`](../examples/custom_game.rs)에 있다.
